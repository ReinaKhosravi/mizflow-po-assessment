# MizFlow recorded walkthrough

Narration is synthesized using the installed macOS Samantha voice. It is not Reina Khosravi’s voice. Application screens are actual read-only captures of the frozen HTTPS deployment; no business mutations were performed for this recording.

## 1. Why this workflow first

This is Miz Flow, an Iranian cafe service application submitted by Reina Khosravi. This walkthrough uses disclosed synthetic narration and captured screens of the frozen application. It is not a recording of the applicant's voice or a real customer shift. The central product decision was to finish one shared workflow, rather than present four shallow modules. A waiter, a cook, and another waiter all touch the same party's order. A useful first release must preserve their intent, not simply draw an attractive order card. The scope was established before implementation and refined through review. The chosen boundary is seating, ordering, preparation, delivery, and table release. Payment, inventory and purchasing remain separate. That is a deliberate reduction in surface area, not a claim that a cafe does not need those activities.

## 2. Iranian context and the hall

The first customer scenario is an independent Iranian cafe with a small floor team. The working interface is Persian and right to left. The hall has twelve active physical tables, numbered one to twelve, with visibly different two seat and four seat shapes. Free, occupied and awaiting order filters help staff find the next action. The picture is illustrative, not a measured floor plan. Recording that a party has been seated and received menus is different from submitting food. A draft seating record occupies the table without appearing as kitchen work. These choices are grounded in the supplied brief and scenario review. They are not presented as findings from merchant interviews. Real devices, internet conditions and staff habits still need a supervised pilot.

## 3. Ordering: intent and money

An authenticated waiter or manager can choose menu items, quantities and preparation notes, then deliberately submit them. The browser does not get to decide the trusted price or restaurant membership. Prices are stored as integer Iranian rials and displayed in toman by dividing by ten. Each submitted line keeps the server's name and price snapshot, so a later menu edit does not rewrite the past. Additional drinks or pizza are appended, not sent as a replacement copy of the entire order. Uncertain submissions retain their original command identity for safe checking. Unsent selections belong to the original party. If another staff member closes and reseats the table, those choices cannot silently become the new guests' food. They are not, however, a durable offline queue.

## 4. Ready is not served; served is not departed

The kitchen sees submitted items with a table number, quantity, preparation note and submission time. Its permitted sequence is queued, preparing, then ready. The waiter separately confirms each ready line that was actually delivered. That records the authenticated actor and server time and removes the line from kitchen work. The party still occupies the table. They can order another round without losing earlier delivery records. Only after guests leave does a waiter or manager confirm table release. Unserved food prevents closure, and the next party receives a different order on the same physical table. This separation avoids a subtle but important error: kitchen readiness is not proof of delivery, and delivery is not proof of departure or payment. This recording only views the frozen application; the actual mutations were exercised in the documented tests.

## 5. Security is below the navigation

There are three roles. A waiter takes and serves orders. Kitchen staff prepare food. A manager can cover either job inside their own restaurant. The manager panel selector changes the working view, not the account's authority. Ordinary staff cannot select themselves into management. More importantly, the navigation is not the security boundary. Server entry points verify the Supabase user and resolve an active membership from trusted database records. Database policies restrict rows, explicit grants restrict operations, and composite foreign keys reject cross restaurant or cross branch relationships. Normal requests use the user's session and a public project key, never the offline administrative key. Revocation is checked against current membership. This is a concrete application boundary, not a claim that a compromised database administrator could be made harmless by row policies.

## 6. Concurrency choices and actual evidence

The concurrency strategy is intentionally simple: serialize changes to one order in PostgreSQL while allowing unrelated orders to progress independently. Narrow transaction functions lock the relevant resources, check versions and record events in the same commit. A unique index is the final protection against two active orders for one table. Idempotency keys are bound to actor, command, target and payload, so a retry does not become a second drink. Actual tests inspect final rows, prices, versions and audit effects, not just successful responses. They include simultaneous appends, kitchen updates racing with additions, duplicate requests, two opens, two waiters serving one line, and closing while food is appended. Thirty one unit tests, thirty one reported PostgreSQL tests and twenty one reported real Supabase tests passed. The final browser matrix was stopped at the requested freeze with eleven passes and one interrupted case. It is not represented as a fully green final matrix.

## 7. What was wrong, and what remains

Several generated choices were wrong. Read only management prevented the owner from covering a waiter. A fixed test table collided with existing orders, while newly generated test tables polluted the shared hall. The final approach borrows a genuinely free physical table. A serialization error code was also used for a final business conflict; real HTTP testing exposed the problem and a forward migration corrected it. The kitchen still has a visible one hundred item limit. Invitations, password recovery, durable drafts, service exceptions and production monitoring are incomplete. Most importantly, no product AI capability was implemented. The brief asks for one, so this is a disclosed gap. A defensible next capability is an explanation of deterministic shift metrics, with a numeric fallback, strict budgets and untrusted notes treated as data. Autonomous restocking is not justified without recipes, stock counts, waste and lead time data.

## 8. A bounded pilot, and the next decisions

The owner handover explains the actual staff steps, connection failures and known limits in plain language, with a Persian guide as well. The next priorities are a useful bounded shift insight, durable recovery, reviewed service exceptions, owner setup, and operational confidence. Scale estimates are explicit assumptions rather than benchmark claims. With three polling screens per restaurant, ten restaurants are a modest pilot, one thousand make repeated reads and identity checks expensive, and one hundred thousand cannot rely on this single central polling path. The architecture should change when measurement justifies it, without weakening tenant separation. The public repository, live HTTPS application, scope, decisions, AI disclosure and verification report let a reviewer inspect the evidence. The purpose of this submission is one defensible workflow and clear ownership of its limits, not an invented production or AI success story.
